# code-security-and-cleanup — maintainer notes

Notes for editing this skill. They are not part of the skill: `SKILL.md` never links here. If you are using the skill on another project, ignore this file.

- **Repo-wide rules** are in `../ai-context.md`. Read it before editing. If you cannot open it (only this folder is open), say so and ask the user to add the parent folder. Do not guess the rules.
- **Record this skill's new decisions here**, as bans or decisions with their reason. Never create a `docs/` folder inside this skill.

## Decisions
- **Explicit invocation only (user's decision, 2026-11-19).** Keep the "run only when the user explicitly invokes it" sentence in the description. `disable-model-invocation` works only in Claude Code, so other agents rely on the words. Why: this skill makes commits.
- **Approval is opt-in.** Only items the user approves are executed. Never bring back "unless the user objects" wording.
- **A plain request is not approval.** `SKILL.md` defines approval. A request to clean up or fix asks for the audit; blanket permission to delete what is provably unused covers REMOVE items only. Why: without a skill, a cleanup request was taken as permission and files were edited unasked (eval 2, both baselines).
- **A dirty working tree stops the apply stage completely, whatever was approved:** no edits and no commits, even for items in other files. Why: in the baselines the no-skill run and the old skill both committed while the user's work sat uncommitted (eval 3).
- **The core stays lean and language-neutral (rebuilt 2026-11-20).** `SKILL.md` holds the gates, the evidence rules and the verdicts; the references hold method, not bug-type checklists. Never bring back the long grep checklist or the 8-phase structure. Why: in the baselines, no skill found every planted issue, and the old checklist skill cost more for no detection gain.
- **Framework depth is added one stack at a time, each with its own fixture and eval (user's decision, 2026-11-19).**
  - The PHP and WordPress fix advice removed with `owasp-checklist.md` is in git history at `a26126d`; re-home it in that stack's reference. It covers `password_hash`, `escapeshellarg` rather than `escapeshellcmd`, and `wp_safe_redirect` followed by `exit`.
  - The performance specifics went with `performance-io-guide.md` (`SELECT *`, Composer `-o` and `-a`). Only an unmeasured risks list remains.
- **The cost is accepted (user's decision, 2026-11-20).** The skill uses about twice the tokens of no skill (1.44× output), mostly in extra turns for the branch, the per-kind commits and the checks. Why: the user values the structure. Never cut those steps to save tokens without re-running the gate evals.
- **Measured on Claude only: this version on Opus 5.5 at high effort, the old one on Fable 5.2. The user accepted this on 2026-11-20.** Antigravity may run another model, and the gates have not been measured there.
- **No metrics tables:** no hand-estimated Maintainability Index, complexity, coupling, duplication or line-count scorecard. Never re-add them. Why: the index's `HV ≈ LOC * 5` shortcut made it follow file length, a real audit report called the metrics flat, and re-running them after every commit cost time for nothing.
- **`strict_types` is not a security control.** The ban is in `SKILL.md`; never list it as a fix for type juggling or tell the agent to add it to existing files. Why: it does not change how `==` works, and adding it can turn working calls into fatal errors.
- **Dead CSS, stale feature flags and duplicates are REVIEW at most.** Never let them reach REMOVE. Why: a search of the repository cannot see database content, a flag's real state, or whether two copies must stay separate.
- **A registered handler is never "dead".** It is unused but reachable. Removing it needs confirmation from the user or access logs.
- **OWASP labels follow the 2025 edition, with the CWE number first.** The mapping in `references/security-review.md` was checked against the OWASP 2025 category pages on 2026-11-19 (A03 on 2026-11-20). Re-check it when a new edition appears. Why: the 2021 numbers had reached a client-facing report.
- **Any search pattern the skill gives must run under `grep -E`.** No lookaheads and no `(?:` groups. Why: those fail or misbehave on stock grep.

## Evals
- **Evals run on generated git fixtures.** `evals/fixtures/setup.sh <scenario> <dest> [state-dir]` builds a fresh repository for one run and writes its state folder (default `<dest>.state/`); `evals/fixtures/check.sh` reads it, from `STATE_DIR` when that is set.
- **A run's own folder holds only the task, the repository and the outputs folder.** Keep the state folder, the assertions and the check command somewhere the agent does not list. Why: in the first baseline runs they sat beside the task, and the state folder's file names alone tell an agent it is being tested.
- **Never store a secret-shaped string, a vulnerable version pin, or a file the root `.gitignore` drops inside a fixture.** `setup.sh` generates them. Why: this repo is public, so a stored key can trip push protection and a stored pin can raise dependency alerts; ignored files would silently go missing from a clone.
- **Fixture file names, function names and comments carry no hints.** No "legacy", "deprecated", "unused" or similar. Why: a name that gives a planted item away makes the eval measure reading names.
- **A run must use a copy of the skill without `evals/`.** Why: that folder holds the planted issues, the reference fixes and the assertions.
- **Examples in `SKILL.md` and `references/` must not reuse a fixture's planted issues or echo an eval prompt's wording.** Why: the evals would then measure recall of the examples. The first draft of the approval rule quoted the gate prompts almost word for word.
- **Run `evals/fixtures/selftest.sh` after changing any fixture or check;** it must end with 0 wrong. Set `PHP_DOCKER_IMAGE` (or have `php` on PATH) so the PHP parse check and the stub run are included.
- **Check names start with `safety_`, `rule_` or `target_`.** Keep a safety failure (true for any agent) apart from a skill rule. Why: a no-skill baseline should not be marked unsafe for skipping a rule only the skill states.
- **The baseline "old skill" is commit `60475b2`,** the version before the 2026-11-19 corrections, measured on Fable 5.2 at max effort. The rebuilt skill was compared with no skill on Opus 5.5 at high effort, at the user's request (2026-11-20).
- **Measure cost by summing usage over every request in a run's transcript.** The per-agent token figure that Claude Code reports is the size of the last request, not the tokens used. Why: that figure made the old skill look 46% dearer when it processed 1.83× the tokens.
- **Detection is at ceiling on these fixtures.** In the 2026-11-19 baseline (Fable 5.2 at max effort with an advisor model and the user's global rules loaded) and again on Opus 5.5 at high effort, every setup found every planted security issue in evals 0 and 4. A weaker setup may not be at ceiling. Never claim a detection gain from these evals; that needs harder seeds. Why: a perfect score here shows the model, not the skill.
- **Weak seed: the plugin's `./polyfills.js` import.** Agents reasonably suggest dropping polyfills that current browsers no longer need, so eval 0's assertion 18 failed in 5 of 6 baseline runs in both setups. When the plugin fixture is next changed, replace it with a side-effect import the plugin plainly needs, and re-run the baseline for evals 0 and 1.
- **The fixture hooks log to the state folder and name its path.** An agent checking that its hooks ran may open that folder; one run did, after its work was done. Fix it by logging to a path that names nothing; until then, inspect any run that opens the folder.
